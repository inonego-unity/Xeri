# 이벤트 알림과 실패 처리

## 배경

이벤트 구독자는 소유자가 통제하지 못하는 코드입니다. 구독자 하나가 예외를 던졌을 때 나머지 구독자, 이미 확정된 상태, 호출자에게 어떤 일이 일어나야 하는지는 이벤트마다 달라야 하지만, 그 선택이 코드마다 따로 구현되면 일관성을 잃습니다. 이 문서는 어떤 이벤트에 어떤 정책을 쓰고 어떤 도구로 구현하는지 정리합니다.

## 핵심 모델

```text
원천                      수집기                    종료 처리
InvokeEach(handler)   →   ExceptionBuffer(ref)  →   ThrowWhenAny / ToException / LogAll
정리 단계의 try/catch
```

- **원천**은 실패를 만드는 곳입니다. 이벤트 구독자 호출이나 정리 단계 하나하나입니다.
- **수집기**는 `ExceptionBuffer`입니다. 정상 경로에는 할당이 없고, 첫 실패가 들어올 때만 목록을 만듭니다.
- **종료 처리**는 모은 실패를 어떻게 끝낼지 정합니다. 던지거나, 값으로 돌려주거나, 로그로 남깁니다.

원천과 단계 함수는 던지지 않고 수집기에 더하기만 합니다. 던지는 것은 **작업의 소유자 한 명**이고, 마지막에 한 번 처리합니다.

## 도구

| 도구 | 역할 |
|---|---|
| `ExceptionBuffer.Add` | 실패를 쌓음. 구조체이므로 다른 메서드에 넘길 때는 `ref`로 넘김 |
| `ExceptionBuffer.ThrowWhenAny(message)` | 없으면 아무것도 하지 않고, 하나면 원래 예외를 스택 그대로, 둘 이상이면 `AggregateException`으로 던짐 |
| `ExceptionBuffer.ToException(message)` | 던지지 않고 없으면 null, 하나면 그 예외, 둘 이상이면 `AggregateException`을 반환 |
| `ExceptionBuffer.LogAll()` | 던지지 않고 쌓인 예외를 하나씩 콘솔에 남김 |
| `EventHelper.InvokeEach(handlers, args…, ref failures)` | 구독자를 하나씩 호출하고 실패를 모음. `Action` 계열(인자 0~4개)과 `EventHandler`, `EventHandler<T>`를 받음 |
| `EventHelper.InvokeEach(handlers, args…, invoke, ref failures)` | 표준 형태가 아닌 델리게이트(사용자 정의)를 호출 방법을 람다로 받아 구독자별로 호출함. 인자는 0~4개 |
| `EventHelper.Handlers()` | 구독자를 읽기 전용 View로 돌려줌. 직접 순회할 때 사용 |

원래 예외와 정리 중 생긴 실패를 함께 던질 때는 새 메서드 없이 `Prepend(원래 예외)` 뒤에 `ThrowWhenAny`를 호출합니다. 정리 실패가 없으면 원래 예외가 그대로 던져집니다.

## 이벤트 종류별 정책

| 종류 | 정책 | 구현 |
|---|---|---|
| 사전 알림 (`…ing`) | 모든 구독자에게 알린 뒤 던져 작업을 중단 | `InvokeEach` + `ThrowWhenAny` |
| 확정 후 알림 (`…ed`, `Changed`, `Ended`) | 이미 확정된 상태를 되돌리지 않고, 모든 구독자에게 알린 뒤 던짐 | `InvokeEach` + `ThrowWhenAny` |
| 종결 트랜잭션 | 단계마다 실패를 모으며 끝까지 진행하고 마지막에 한 번 던짐 | `ExceptionBuffer` + 단계의 `try/catch` |
| 순서·게이트 알림 | 첫 실패에서 중단하고 구독자 사이마다 조건을 확인 | `Handlers()` 직접 순회 |
| 표현 계층 알림 | 실패가 흐름을 끊지 않게 격리하고 로그만 남김 | `Handlers()` 순회 + `LogAll` |
| 단순 값 변경 | 단순 호출, 구독자 예외는 호출자에게 전파 | `?.Invoke` |

도메인·Foundation 계층은 모아서 던지고, 표현·UI 계층은 로그로 남기는 것이 기본입니다.

## 규칙

- 실패를 모으는 버퍼는 `ref ExceptionBuffer`로 넘깁니다. 값으로 복사해 넘기면 목록이 아직 없을 때 첫 `Add`가 복사본에서만 일어나 실패를 잃을 수 있습니다.
- 구독자 호출 캐시는 **같은 델리게이트 객체를 여러 번 알리고 구독이 안정적인 이벤트**에만 맞습니다. 객체마다 한두 번만 알리는 이벤트나 구독을 자주 바꾸는 이벤트는 알릴 때마다 목록을 새로 만들어 이득이 없습니다.
- 알림 도중 구독이 바뀌어도 호출 시작 시점의 구독자 목록으로 끝까지 호출합니다. 한 번의 처리에서 여러 번 알릴 때 같은 목록을 쓰려면 델리게이트를 지역 변수에 한 번 담아 씁니다.
- 구독자 격리가 필요한 이벤트는 가능하면 `Action` 계열이나 `EventHandler` 계열로 선언합니다. 표준 형태가 아닌 사용자 정의 델리게이트는 호출 방법을 람다로 넘기는 `InvokeEach` 오버로드를 쓰고, 이때 람다에는 `static`을 붙여 바깥 값 캡처와 호출마다의 델리게이트 할당을 피합니다. `static`을 강제하지는 않으므로 캡처하는 람다를 넘기면 호출마다 할당합니다. `in`/`ref` 매개변수 델리게이트처럼 람다로도 다루기 어려운 이벤트는 `Handlers()`로 직접 순회합니다.
- 구독 함수는 코드에서 `handler`라고 부릅니다. `observer`는 쓰지 않습니다. `callback`은 일회성 후속 동작을 인자로 받을 때만 씁니다.
- 알림 중 재진입과 순서는 이 도구가 다루지 않고 소유자가 정합니다. 구독자가 상태를 바꾸지 못해야 하면 재진입 차단 플래그로 거절하고, 구독자가 새 명령을 내려도 되어야 하면 알림을 큐에 쌓아 바깥 전달 루프가 순서대로 전달하게 합니다.

## 이 모델이 덮지 않는 것

다음은 이 모델의 범위 밖이며 각자 구조로 처리합니다.

- 첫 실패에서 중단하는 흐름과 구독자 사이 게이트
- `finally`로 소유자의 자원 반환을 보장하는 흐름
- 정리 실패를 되돌리는 보상 트랜잭션의 로직
- 예외가 아닌 실패 결과(`Reject` 같은 반환값, 검증 `Diagnostic`)
- 재진입 차단과 알림 순서 제어
- 구독자 예외를 호출자에게 그대로 전파하는 단순 값 변경 이벤트
